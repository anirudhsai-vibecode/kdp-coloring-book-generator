## Problem Statement

Side hustlers publishing coloring books on Amazon KDP spend 20+ hours per book manually designing pages in Illustrator/Canva. This time burden causes them to quit KDP entirely — they can't sustain the weekend-only grind alongside a day job. The core problem is **time**, not idea generation or market access.

- **Current workaround cost:** "Manual design in Illustrator/Canva — 20+ hours per book"
- **User is the target customer:** Building for their own use case first, with observed community demand in KDP Facebook groups/Discords
- **Behavioral evidence:** User has already invested in building a sophisticated CLI with Cloudflare multi-account rotation, theme lock, QA gates, and PDF compliance — this is not hypothetical interest

## Status Quo

Users today either:
1. **Manual design** in Illustrator/Canva — 20+ hours/book, high skill barrier
2. **Hire illustrators** on Fiverr/Upwork — $200-500/book, communication overhead, inconsistent quality
3. **Other AI generators** (Midjourney, DALL-E) + manual cleanup in Photoshop — prompt engineering trial-and-error, no KDP format compliance
4. **PLR/royalty-free bundles** — licensing risk, generic art, reformatting time

All paths require significant manual labor or money. No existing tool generates **print-ready, KDP-compliant PDFs (interior + cover)** end-to-end with theme consistency and automated QA.

## Target User & Narrowest Wedge

**Target human:** Side hustler with a day job, publishing on weekends only. Constraint: time. Fear: giving up on KDP because the production grind is unsustainable.

**Narrowest wedge (Approach B — Native Web App with Task Queue):**
- Web UI where user picks theme, page count, author name
- Async job queue handles generation (Cloudflare rotation, QA gates, retries)
- Real-time progress via WebSocket
- Downloads compliant interior.pdf + cover.pdf ready for KDP upload
- User accounts + book history for repeat publishing

This is the smallest version someone would pay for — not a CLI wrapper, not a desktop app. A web app with proper async UX removes the "weekend only" constraint by letting generation run while they do other things.

## Constraints

- **Must use Cloudflare Workers AI (FLUX.1-schnell)** — free tier ~10k neurons/day/account; multi-account rotation on 429/4006
- **KDP format compliance is non-negotiable** — 8.5×11 trim, 0.125" bleed, spine calculation, even page counts, barcode zone
- **Theme lock must hold** — pets theme = pet subjects only; garden chores/jars rejected
- **QA gates are hard requirements** — canvas 2550×3300, pure B&W, 0.5" margins, no solid fills, no wire grids, eyes/pupils heuristic, chore-class duplicate detection
- **User review gate** — `--require-user-review` (default on) blocks packaging until explicit approval
- **No Pollinations/Hugging Face fallback** — Cloudflare only (by design)

## Approaches Considered

### Approach A: Minimal Web Wrapper (ship this weekend)
- Thin FastAPI wrapper around existing CLI; subprocess calls `main.py`; streams logs via SSE; downloads ZIP
- Effort: S (2-3 days) | Risk: Low
- Pros: Ships fastest, zero logic rewrite, same QA gates
- Cons: Subprocess fragile at scale, no auth/multi-user, request timeouts on free hosting

### Approach B: Native Web App with Task Queue (CHOSEN)
- FastAPI + Redis/RQ (or Celery); async job queue; WebSocket progress; user accounts + book history; Cloudflare rotation server-side; PostgreSQL for metadata
- Effort: L (3-4 weeks) | Risk: Medium
- Pros: Scales to real users, proper async UX (no timeouts), multi-tenant ready, observability built-in
- Cons: Significant new code, infra costs (Redis, DB, workers), longer to first dollar

### Approach C: Local-First Tauri/Electron Desktop App
- Package Python CLI + React/Vue frontend in Tauri; runs on user's machine; uses their Cloudflare keys locally; no server costs
- Effort: M (2-3 weeks) | Risk: Medium
- Pros: Zero hosting cost, user owns data/keys, works offline (dry-run), native FS access
- Cons: No cloud queue (limited by local CPU), install friction, cross-platform testing burden

## Recommended Approach

**Approach B: Native Web App with Task Queue**

Rationale: The user's wedge is "publish this weekend" but they chose B over A — signaling they want a **real product foundation**, not a throwaway wrapper. The Cloudflare quota opacity pain they identified ("no clear resume path") is solved by server-side job queues with persistence and retry. A subprocess wrapper (A) cannot solve this — if the request times out or the browser closes, the job is lost. A proper queue (B) makes the quota rotation, retries, and resume behavior reliable and observable.

The 3-4 week investment pays off because:
- All existing Python logic (image_gen, themes, pdf_builder, qa_gate) becomes a clean library called by workers
- Multi-account Cloudflare rotation becomes a managed server-side service
- Failed_dump archiving and user review gates become first-class web UX
- Foundation for multi-user, billing, and future features (template marketplace, auto-publish to KDP API)

## Open Questions

1. **Auth strategy:** Start with magic-link email (simpler) or GitHub OAuth (dev-friendly)? Recommend magic-link for non-technical KDP publishers.
2. **Hosting target:** Fly.io (simpler Redis/Postgres) vs Railway vs Render? Fly.io has generous free tier and native Redis.
3. **Billing model:** Per-book credit packs vs monthly subscription? Credit packs align with "side hustler" cash flow.
4. **KDP auto-publish API:** Amazon doesn't have a public upload API — defer to v2. Manual upload is acceptable for wedge.
5. **Image model upgrade path:** FLUX.1-schnell → FLUX.1-dev or SDXL when quality demands it? Architecture should abstract provider.

- **Database migrations:** Run on deploy via Fly.io release command

## Dependencies

- **Python CLI stability:** Current `main.py` must be refactorable into importable library (no `sys.exit()` in library paths)
- **Redis + PostgreSQL:** Fly.io provides both; need connection pooling for worker concurrency
- **WebSocket scaling:** Single worker process handles SSE; if horizontal scaling needed later, add Redis pub/sub
- **Cloudflare account provisioning:** User onboarding flow must guide them to create Workers AI tokens
